## Summary

**Scenario A — SDN (Mininet, Open vSwitch, OS-Ken).**
- A three-switch, four-host network runs under an external Dockerized OS-Ken controller over OpenFlow 1.3, with
  fail-mode `secure` and 100 Mbit/s TBF + 1 ms netem shaping on all six links.
- The learning switch gives 0 % loss on `pingall`. The h1→h4 path (s1 port 1→3, s2 1→2, s3 3→2) is proven from the flow
  tables before any measurement.
- UDP at 50 / 80 / 100 Mbit/s offered gives 49.95 / 79.71 / 96.82 Mbit/s received with 0 / 0.23 / 1.93 % loss; TCP reaches
  92.6 Mbit/s.
- In the 50 Mbit/s observability experiment the h1→h4 flow rule counts **43,175 packets and 64,309,891 bytes on all
  three switches**, and the inter-switch port counters agree on both links.
- A two-table traffic classifier identifies 10/10 generated data flows correctly. Its policy (an OpenFlow meter on
  bulk UDP) raises a competing TCP flow from 16.1 to 79.0 Mbit/s.

**Scenario B — O-RAN (OCUDU gNB, srsUE, FlexRIC, Open5GS).**
- No course image was provided, so the gNB, the UE and the RIC were compiled from source.
- The srsUE registers through the OCUDU gNB on the Project 2 Open5GS core and exchanges traffic in both directions.
  The gNB completes E2 Setup with FlexRIC and registers KPM (RAN function 2) and RC (RAN function 3).
- A custom KPM xApp exports five measurements to CSV once per second. Their units were checked in the OCUDU source.
- An Edge-AI xApp classifies the load from PRB utilization and RLC delay. A dry-run Resource-Management xApp turns the
  states into recommendations; it never sends a control request.
- Over a nine-run campaign, 5 / 12 / 18 Mbit/s downlink use 15 / 38 / 57–61 % of the PRBs with ~1.5 ms RLC delay and no
  loss. Congestion appears only above 25 Mbit/s (PRBs capped at 84 %, delay ≈ 1.6 s, 6–29 % loss).
- An optional decision tree reaches 99.1 % accuracy on three runs it never saw during training.

## A.3 Learning switch (Phase 6)

[`learning_switch.py`](ScenarioA/controller/learning_switch.py) installs a table-miss rule (priority 0 → controller),
learns source MAC → ingress port on every packet-in, floods unknown destinations and installs a priority-1 rule once
the destination is known. `pingall` gives 0 % loss (12/12). Before the ping each table holds only the table-miss
rule; after it, the learned rules are present (`phase6_before_ping_flows_*`, `phase6_after_ping_flows_*`).

**A bug found by measurement.** The first version matched on the destination MAC only. `pingall` passed, but UDP at
50 Mbit/s delivered 17.9 Mbit/s with 43.6 % loss. The flow tables showed no rule toward h4 on any switch: once a
rule "toward h1" existed, replies from h4 no longer reached the controller, so h4 was never learned and all h1→h4
traffic went through the controller (43,176 table-miss packets on s1 during one test). The rules now match
`(in_port, eth_src, eth_dst)`, so a frame from an unknown source always reaches the controller. The measurement
script also refuses to measure until the h1→h4 rule exists on s1, s2 and s3 with the expected output ports
(`phase6_path_h1_h4.txt`). The failed run is kept in
[`invalid-run-20261116T124705Z-dst-only-match`](ScenarioA/experiments/invalid-run-20261116T124705Z-dst-only-match/).

| Observation | Value |
|---|---|
| iperf3 | 49.99 sent, 49.94 Mbit/s received, 6 / 43,160 datagrams lost |
| h1→h4 flow rule delta on s1, s2, s3 | **43,175 packets, 64,309,891 bytes — identical on the three switches** |
| s1:3 tx vs s2:1 rx, s2:2 tx vs s3:3 rx | 43,175 packets and 64,309,891 bytes on both sides of both links |
| Table-miss delta during the test | 2 / 1 / 2 packets (traffic is forwarded by the switches, not the controller) |
| PCAP | 25,000 packets, all 10.0.0.1 → 10.0.0.4 UDP port 5201, 1,490-byte frames |

The reference reports 43,183 packets and 64,314,561 bytes for the same experiment.

**Aggregate versus protocol-specific counters.** The rule matches MAC addresses, so it counts all h1→h4 traffic. It
shows 15 packets more than the 43,160 UDP datagrams: the iperf3 TCP control connection and the preparation ping.

**Snapshot timing.** In a first valid run the flow counters were about 1,300 packets behind the port counters and
differed between switches. OVS pushes datapath flow statistics to the OpenFlow tables in batches of about one second,
while port counters are read directly. The script now waits 4 s with no traffic before each snapshot. Each snapshot
is timestamped per switch, so the byte delta is normalized over the real snapshot interval (15.6 s → 33 Mbit/s
average); that value includes idle time and must not be compared with the iperf3 rate. The earlier run is kept in
[`run-20261116T125209Z-snapshots-trop-tot`](ScenarioA/experiments/run-20261116T125209Z-snapshots-trop-tot/).

## A.7 Traffic classification and SDN policy (Phase 10)

**Design** — [`classifier_switch.py`](ScenarioA/controller/classifier_switch.py). Each switch uses two tables:

- **Table 0 (classification):** one rule per TCP/UDP flow (5-tuple, priority 10) that goes to table 1; the first
  packet of an unknown flow goes to the controller, which creates the flow state and installs the rule.
- **Table 1 (forwarding):** the learning switch of Phase 6, unchanged.

Classification therefore never changes forwarding. Every second the controller reads the table-0 counters of each
flow on its ingress switch and computes the rate and the mean packet size. The decision rule is transparent:
**BULK** if rate ≥ 10 Mbit/s and mean packet size ≥ 1,000 bytes for two consecutive intervals, otherwise **LIGHT**;
the class is the protocol plus BULK/LIGHT. A LIGHT flow can become BULK later, never the reverse. The thresholds
separate the generated classes with a wide margin (bulk flows ≥ 50 Mbit/s, light flows ≤ 2 Mbit/s).

**Policy.** A flow classified `UDP_BULK` is limited to 20 Mbit/s by an OpenFlow meter on its ingress switch. The same
protocol is played twice: `monitor` (classify only, the control experiment) and `enforce` (policy applied).

**Classification against ground truth** (`classification_validation.csv`). Ground truth is the iperf3 command.

| Generated flow | Expected | Decided (both modes) | Rate at decision | Mean packet |
|---|---|---|---|---|
| TCP h1→h4 | TCP_BULK | TCP_BULK | ≈ 99 Mbit/s | > 1,900 B |
| UDP 50 Mbit/s | UDP_BULK | UDP_BULK | ≈ 51.5 Mbit/s | 1,490 B |
| UDP 1 Mbit/s, 200-byte payload | UDP_LIGHT | UDP_LIGHT | ≈ 1.2 Mbit/s | 242 B |
| TCP h2→h3 (competition) | TCP_BULK | TCP_BULK | 16–20 Mbit/s | > 2,600 B |
| UDP 80 Mbit/s (competition) | UDP_BULK | UDP_BULK | 82–84 Mbit/s | 1,490 B |

10/10 data flows are correct, decided 2–3 s after the flow starts. Of 30 side flows (iperf3 control connections, TCP
ACK streams, UDP return traffic), 16 are LIGHT, 14 are too short to classify and none is wrongly BULK.

**Policy evaluation** — TCP h2→h3 competing with UDP 80 Mbit/s h1→h4 on the same links for 20 s:

| Measure | monitor | enforce |
|---|---|---|
| TCP, steady state t ≥ 6 s (Mbit/s) | 16.1 | **79.0** |
| TCP retransmits | 96 | 38 |
| UDP received, from the PCAP on h4 in steady state (Mbit/s) | 83.1 | **19.8** |
| UDP loss | 0.12 % | 65.8 % |
| UDP jitter (ms) | 0.179 | 0.425 |
| Packets dropped by meter 1 on s1 | 0 | 104,471 |

The flow-table change is visible on s1:
`priority=10,udp,in_port=1,nw_src=10.0.0.1,nw_dst=10.0.0.4,…,tp_dst=5201 → meter:1,goto_table:1`. The 65.8 % UDP loss
in `enforce` is the intended effect of the meter, not a link fault. 21/21 automated checks pass.

## A.8 Known limitations

- The policy starts 2–3 s after a flow begins; until then the bulk UDP flow is not limited.
- Classes and thresholds are validated on controlled iperf3 traffic only.
- The classifier never forgets a flow, which is acceptable for short experiments but not for long operation.
- The optional multi-path extension was not implemented.
- Flow rules have no timeout in the learning switch; a host that moves would not be relearned.

## B.5 Extended KPM measurements and CSV export (Phase 7)

[`xapp_kpm_csv.c`](ScenarioB/xapps/kpm/xapp_kpm_csv.c) subscribes to five measurements and writes one CSV line per
indication until it receives SIGTERM. Columns are documented in
[`kpm_columns.csv`](ScenarioB/xapps/kpm/kpm_columns.csv).

| Measurement | Unit (from `e2sm_kpm_metric_defs.h` in OCUDU) | Meaning in this build |
|---|---|---|
| `DRB.UEThpDl`, `DRB.UEThpUl` | kbit/s | RLC PDU bytes (headers included) over the DU metrics period |
| `RRU.PrbTotDl`, `RRU.PrbTotUl` | % (integer) | mean PRBs used per slot / cell PRBs × 100 |
| `DRB.RlcSduDelayDl` | 0.1 ms | mean downlink RLC SDU delay; **no value** when no SDU was sent |

- **Order.** With five measurements the gNB does return the measurement names, in the requested order. The xApp
  records them (`reported_names`) and maps values by subscription order, with a `mapping_status` column that flags any
  count mismatch. No mismatch occurred (0 invalid lines in nine runs).
- **Scope.** Values are at E2-node (cell) level. UE and cell identifiers are not in the Format 1 indication and are
  written as `unavailable`, not inferred.
- **Timestamp.** The observation time is the xApp reception time. `collectStartTime` is kept raw and not used.
- **Achieved rate versus offered rate.** KPM throughput is about 1.10 × the iperf3 offered rate. Two causes were
  identified: the ZeroMQ radio runs slower than real time (median interval between indications 1,076–1,091 ms over the nine
  campaign runs, instead of 1,000),
  and KPM counts RLC PDUs with their headers.

## B.6 Edge-AI xApp (Phase 8)

[`edge_ai.py`](ScenarioB/xapps/edge_ai/edge_ai.py). **Data exchange:** a shared CSV file in the run directory
(`kpm.csv`), followed as it grows; only complete lines are read; one record per indication; timestamps are Unix
seconds from the KPM xApp. Duplicates are dropped, invalid lines are written with `valid=0` and excluded, and an
absent RLC delay stays absent rather than becoming zero.

**Features:** 3-indication moving averages of throughput, PRB utilization and RLC delay, and the downlink throughput
trend over 5 indications.

**Rule-based baseline (`rules-v1`).** Thresholds come from the calibration run
[`calib-dl-01`](ScenarioB/experiments/calib-dl-01/):

| Downlink offered | PRB DL | RLC delay | Loss |
|---|---|---|---|
| 5 Mbit/s | 15 % | 1.06 ms | 0 % |
| 12 Mbit/s | 38 % | 1.55 ms | 0 % |
| 18 Mbit/s | 59 % | 1.38 ms | 0 % |
| 25 Mbit/s | 84 % | 38 ms | 0 % |
| 32 Mbit/s | 84 % | ≈ 1.25 s | 5.8 % |
| 40 Mbit/s | 84 % | ≈ 1.65 s | 21.4 % |

- Load = max(PRB DL, PRB UL), smoothed. **NORMAL** below 50 %, **ELEVATED** from 50 %, **HIGH** from 80 %.
- **Congestion** = HIGH and smoothed RLC delay ≥ 10 ms (about seven times the uncongested value).
- High throughput alone never produces a congestion flag: 18 Mbit/s uses 59 % of the PRBs with a normal delay.

**Optional model.** [`train_tree.py`](ScenarioB/xapps/edge_ai/train_tree.py) trains a depth-2 decision tree on the
smoothed downlink throughput, labelled low / normal / high from the offered 5 / 12 / 18 Mbit/s. Training uses two
whole runs; evaluation uses three other runs, so adjacent samples are never split between the two sets. The tree is
exported as readable JSON ([`model.json`](ScenarioB/xapps/edge_ai/model/model.json), version `dt-v1-c1`).

| | Samples | Accuracy |
|---|---|---|
| Training runs (`c1-train-01`, `c1-train-02`) | 118 | 100 % |
| New runs (`c1-eval-01` to `-03`), steady state | 227 | **99.1 %** |

The learned thresholds are 8.12 and 14.79 Mbit/s. The two errors on new runs are at the edge of a traffic step. These
thresholds belong to this feature and this testbed. The instructor model cited in the guide (12.06 and 20.72 Mbit/s)
was not available, so no comparison with it is made.

Each output line holds the analysis timestamp, the measurements, the features, the rule state with its reason, the
congestion flag, and the model state, confidence and version (`edge_ai.csv`).

## B.7 Resource-Management xApp (Phase 9)

[`resource_mgmt.py`](ScenarioB/xapps/resource_mgmt/resource_mgmt.py) reads `edge_ai.csv` and writes
`rm_decisions.csv`. It runs in **DRY_RUN** mode only: every record has `execution_mode=DRY_RUN` and
`control_request_sent=0`, and the application never contacts the RIC or the gNB.

| Condition | Recommendation |
|---|---|
| NORMAL | `MAINTAIN_CURRENT_ALLOCATION` |
| ELEVATED, or HIGH without confirmed congestion | `CONTINUE_MONITORING` |
| HIGH with congestion (delay ≥ 10 ms) | `REVIEW_RESOURCE_ALLOCATION` |
| HIGH from uplink PRBs for 5 evaluations | `REVIEW_RESOURCE_ALLOCATION` |

**Stability.** The recommendation changes only after the same candidate is seen three times in a row and at least
5 s after the previous change. Each record gives the policy condition, the candidate, its streak, the outcome
(`UNCHANGED`, `HELD_…`, `CHANGED`) and the policy version.

## B.8 Integrated experiments (Phase 10)

[`run_campaign.sh`](ScenarioB/experiments/run_campaign.sh) runs nine experiments with

aligns the three xApp outputs with the traffic segments by timestamp. Traffic is iperf3 UDP started on the UE side:
without option the UE sends (uplink); with `-R` the data endpoint sends (downlink). `segments.csv` records sender and
receiver for every segment. Steady state is from 3 s after the start to 1 s before the end of a segment.

**Downlink, three repetitions** (`c1-eval-01` to `-03`), 25 s per level:

| 18 Mbit/s | 18.00, 0 % loss | 20.05–21.10 | 57–61 % | 1.38–1.58 ms | ELEVATED | CONTINUE_MONITORING |

States and recommendations are identical across the three repetitions.

**Saturation** (`c1-saturation`):

| Offered | iperf3 received | Loss | PRB DL | RLC delay | State | Congestion | Recommendation |
|---|---|---|---|---|---|---|---|
| 25 Mbit/s | 25.00 | 0 % | 80 % | 1.60 ms | HIGH 69 % of the time | no | CONTINUE_MONITORING |

8 load transitions.

| Offered | iperf3 received | Loss | PRB UL | State |
|---|---|---|---|---|
| 1 Mbit/s | 1.00 | 0 % | 38–40 % | NORMAL |
| 2 Mbit/s | 2.00 | 0 % | 61–63 % | ELEVATED |
| 3 Mbit/s | 3.00 | 0 % | 92 % | HIGH |
| 5 Mbit/s | 4.89–4.92 | 0.9–1.3 % | 96 % | HIGH |

Uplink capacity is far lower than downlink. There is no uplink delay measurement, so a HIGH uplink state is reported
as "uplink saturation suspected" and never as congestion.

**Responsiveness.** The final state of a segment is reached 3–5 s after a step that changes the state (three-sample
smoothing), and the recommendation about 2 s later (three consecutive evaluations).

**What is not claimed.** The Resource-Management xApp is dry-run. Its recommendations are evaluated for correctness,
stability and explainability only. No throughput, latency or resource-utilization improvement is claimed, because no
control action was executed.

## B.9 Problems met and how they were solved

| Symptom | Cause | Fix |
|---|---|---|
| gNB exits: `Channel gain must be <= 0.0 dB for ZMQ-device` | OCUDU rejects positive gains with ZeroMQ | `tx_gain: 0`, `rx_gain: 0` |
| `Registration reject [95]`, AMF `HTTP response error [400]`, SCP `No SEPP` | NRF served only 999/70, so a 001/01 subscriber was treated as a roamer | add 001/01 to the NRF `serving` list |
| srsUE `Unable to unpack complete NAS pdu` on Registration Accept | the AMF sent a TAI list with two PLMNs, which srsUE cannot decode | AMF serves the 001/01 TAI only |
| UE stuck at `Attaching UE...` after a restart | the ZeroMQ radio is a request/reply exchange; restarting one side blocks the other | always recreate gNB and UE together, UE after the gNB (`ran-up.sh`) |
| `setting the network namespace "ue1" failed` | stale `/run/netns/ue1` after `docker restart` | delete and recreate the namespace at start |
| Empty container logs | stdout buffered without a terminal | `stdbuf -oL` |

## B.10 Known limitations

- **Single UE, single cell.** The set-up validates connectivity, measurement, analysis and decision generation. It does
  not show multi-UE contention, scheduling fairness, slice isolation or load balancing.
- **E2SM-RC not tested.** The RC RAN function is registered, which shows that the service model is available, not that
  any control action is implemented by this gNB. No control request was sent.
- **Edge-AI and Resource-Management do not use the FlexRIC SDK.** They exchange data through CSV files and have no
  E42 connection; only the KPM xApp is a FlexRIC xApp. The guide expects the Resource-Management xApp to use the SDK.
- **Missing indications.** About one KPM indication in thirty is missing (a gap of ≈ 2 s instead of ≈ 1.08 s),
  independently of traffic. The WSL2 clock adjustment seen in Project 1 is the suspected cause; this was not proven.
  `delta_prev_ms` records every gap.
- **Slower than real time.** The ZeroMQ radio runs about 8–9 % slower than the wall clock on this machine, so KPM rates per
  radio second are higher than iperf3 rates per wall second.
- **Decision tree limited to throughput.** It cannot separate 18 Mbit/s from saturation, and it was trained and tested
  on one campaign on one day.
- **No uplink delay metric**, so uplink congestion cannot be confirmed.
- **Core shared with Project 2.** The Project 3 core configuration and the Project 2 UERANSIM RAN cannot be used at
  the same time.
- **Images are built for this CPU** (`-march=native` default in OCUDU) and are not portable to an older processor.
